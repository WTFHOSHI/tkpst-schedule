# Vercel и Neon

Публичное приложение: **https://tkpst-schedule.vercel.app/**.

Vercel project: `tkpst-schedule` (`prj_l65yfJSTXnsq28UOd72JhBkcEyrx`). Neon project: `tkpst-schedule` (`fancy-butterfly-66288752`), организация Free, регион Frankfurt. Используются бесплатные планы; платные функции не включались.

## Устройство

- `web/` → `npm run build` → `dist/`: только публичные файлы приложения.
- `/api/*` → Vercel Function `api/index.mjs` в Frankfurt, Node.js 24.x.
- Аккаунты, хеши сеансов и лимиты попыток находятся в Neon Postgres. SQLite в облаке не создаётся.
- `DATABASE_URL` задан как Sensitive-переменная Vercel, только для Production. Значение не включено в код, `dist/` или этот документ. Локальная копия подключения — в исключённом из Git `.env.cloud`.
- Схема создаётся отдельной командой, не при каждом запуске функции.
- В облаке принимаются только origin из доверенных переменных Vercel или явного `PUBLIC_ORIGIN`; присланный Host не определяет доверие. Для собственного домена укажите его HTTPS-origin.
- Cookie — `__Host-…; Secure; HttpOnly; SameSite=Lax`. Приватные API используют POST и `no-store`, сохраняя защиту при обновлении старого service worker.
- Лимиты общие для всех экземпляров функций: один атомарный UPSERT на bucket. Обслуживание просроченных записей выполняется отдельно, без встречных блокировок разных bucket в запросе входа.

Замены и объявления `/overrides.json` проксируются с действующего GitHub Pages приложения. Поэтому изменения существующей админ-панели не зависят от ручного обновления Vercel. Расписание и автобусы продолжают использовать прежние API.

## Проверки

`npm ci`, `npm test`, `npm run build`. В тестах Postgres используется PGlite — настоящий PostgreSQL в WASM. Дополнительно выполнены миграция и изолированные HTTP-проверки реального Neon/Vercel:

```sh
node scripts/smoke-cloud.mjs https://tkpst-schedule.vercel.app
```

Проверены регистрация, восстановление сеанса, профиль, личный журнал без демонстрационных оценок, выход, отказ при неверном пароле, повторный вход, защищённые cookie, запрет приватных GET и недоступность серверных файлов/секретов. Команда создаёт один синтетический аккаунт `qa_cloud_*` и отзывает его сеансы; пользовательские сеансы браузера не меняет.

Через браузер проверен вход в перенесённый аккаунт. После этого пользователь начал самостоятельную регистрацию; введённые им данные и текущая форма сохранены. Остальные проверки проведены отдельным HTTP-клиентом.

Независимая проверка нашла потенциальную взаимную блокировку при одновременной очистке чужих rate bucket и UPSERT текущего. Очистка вынесена из пути запроса. Других существенных замечаний обзор не выявил.

## Миграция и запуск

Создание схемы:

```sh
node --env-file=.env.cloud server/migrate.mjs
```

Разовый перенос локальных аккаунтов, сначала проверка количества:

```sh
node --env-file=.env.cloud server/import-sqlite.mjs
node --env-file=.env.cloud server/import-sqlite.mjs --apply
```

Перенесён один существовавший локальный аккаунт. ID и хеш пароля сохранены, повторная регистрация для него не нужна. SQLite открывается только для чтения, аккаунты в Neon добавляются одной транзакцией; конфликты откатывают весь импорт. Сеансы не копируются, исходная база не изменяется. Повторный импорт без проверки конфликтов не запускайте.

Локально без DATABASE_URL по-прежнему работает SQLite: `npm start`. Для локальной работы с Neon: `node --env-file=.env.cloud server/index.mjs` (после остановки другого процесса на том же порту).

Периодическое обслуживание просроченных записей:

```sh
node --env-file=.env.cloud server/maintenance.mjs
```

## Последующие публикации

Эта версия опубликована напрямую из текущего рабочего каталога через подключение Vercel, без push и без изменения ветки main на GitHub. Автоматическая публикация изменений кода из Git пока не настроена. Файл `scripts/deployment-files.mjs` формирует список файлов для отправки, исключая `.env`, SQLite, `node_modules`, тесты и скриншоты.

Для публикации через CLI после авторизации: `npx vercel --prod`, выбирая существующий проект `tkpst-schedule`. Либо повторить отправку файлов через интеграцию Vercel. Настройки сборки уже записаны в `vercel.json`. Предварительные Preview-развёртывания не имеют DATABASE_URL; для них нужен отдельный Neon branch/подключение и отдельная переменная, чтобы тестирование не затрагивало Production.

Реальные оценки колледжа и восстановление пароля остаются неподключёнными. Регистрация создаёт аккаунт приложения; подтверждение студента для будущего доступа к журналу должно выполняться на сервере.
